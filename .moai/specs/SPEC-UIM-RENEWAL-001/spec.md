# SPEC-UIM-RENEWAL-001

## 1. 배경

기존 usherinmaking 사이트는 **LOCATION(야외 로케이션 촬영) 단일 사업**을 전제로 만들어진 정적
HTML 사이트다. 여기에 **STUDIO(실내 스튜디오)** 가 새로 생기면서, 한 축을 다른 축의 하위로 두는
기존 정보 구조로는 두 사업을 동등하게 보여줄 수 없게 되었다.

디자인 핸드오프(`Usher in Making 리뉴얼 디자인.zip`)는 이 문제를 전제로 확정된 hifi 시안이며,
이 SPEC은 그 시안을 코드베이스에서 재현하는 범위를 정한다.

## 2. 목표

1. LOCATION / STUDIO **2대 축** 구조로 사이트를 다시 짠다.
2. 日本語(기본) / English / 한국어 3개 언어를 **각각 독립된 본문**으로 운영한다.
3. Instagram에 쌓인 사진을 **전량 자동 수집 → 관리자가 전시할 것만 선택 → 자사 도메인에서 서빙**
   하는 파이프라인을 만든다. 임베드·아웃링크를 쓰지 않아 SEO/AEO 손실을 막는다.

## 3. 범위

### 3.1 포함

- Next.js 15 App Router + TypeScript로 전면 재구축 (기존 정적 사이트는 `legacy/`로 보존)
- 공개 페이지 3개 언어분: HOME / STUDIO / LOCATION / DRESS / PLAN / PHOTOGRAPHER /
  JOURNAL(목록·상세) / GALLERY(목록·경로형 필터·작품 상세) / CONTACT / 404 / privacy / tokushoho
- 관리자 8개 화면: 대시보드 / 사진 전시 선별 / 문의 INBOX / 플랜·옵션 / 카테고리·SEO /
  촬영후기 / 번역 / 드레스 / 설정 / 미디어·로그
- 데이터 모델(`prisma/schema.prisma`)과 서버 레포지토리 계층
- 문의 API, 관리자 API, 인스타 수집 크론의 오케스트레이션
- hreflang 상호 지정, 경로 기반 갤러리 필터, sitemap / robots, 구조화 데이터

### 3.2 제외 (이번 SPEC 밖)

- 실제 데이터베이스 연결 및 Prisma 클라이언트 생성 — 스키마와 이관 지점(seam)까지만
- 오브젝트 스토리지 업로드, AVIF/WebP 실제 인코딩 — 계약과 상수까지만
- Instagram Graph API 실호출, AI 분류 실호출 — 자격 증명이 없다
- 정식 관리자 인증 — `ADMIN_TOKEN` 기반 임시 가드까지만
- 로고 SVG 제작 (원본이 195×48 저해상도)

## 5. 요구사항 (EARS)

### 5.1 정보 구조

- **REQ-IA-001** 시스템은 모든 공개 페이지를 `/{locale}/...` 경로로 제공해야 한다
  (`locale ∈ {ja, en, ko}`, 기본 `ja`).
- **REQ-IA-002** 요금 페이지의 URL 세그먼트는 로케일별로 다르다 — `ja: plan`, `en: plans`, `ko: plan`.
  각 로케일은 자기 세그먼트에서만 200을 반환하고 나머지는 404여야 한다 (canonical 중복 방지).
- **REQ-IA-003** 갤러리 필터는 쿼리스트링이 아니라 **경로**여야 한다
  (`/ja/gallery/studio/self-wedding`). 각 조합은 독립 페이지 + 독립 canonical을 가진다.
- **REQ-IA-004** 최초 진입 시 `Accept-Language`로 로케일을 감지해 리다이렉트하고, 선택은 쿠키에
  저장해야 한다. 헤더에서 수동 전환이 가능해야 한다.
- **REQ-IA-005** 모든 페이지는 3개 언어 간 `hreflang` 상호 지정 + `x-default`를 가져야 한다.

### 5.2 콘텐츠

- **REQ-CT-001** 각 페이지는 본문 최상단에 **정의형 1문단**(질문 → 답 형태)을 실제 텍스트로
  가져야 한다. 이미지 안의 글자는 이 요구를 충족하지 않는다.
- **REQ-CT-002** 3개 언어는 서로의 번역이 아니라 독립 본문이다. 한 언어의 본문을 기계번역해
  다른 언어를 채우면 안 된다.
- **REQ-CT-003** 촬영후기는 현재 전부 샘플이다. 시스템은 샘플 글을 실제 후기와 구분되도록
  배지로 표시해야 한다.
- **REQ-CT-004** 미확정 사실(스튜디오 주소, 공항 소요시간, 대표 이메일, 작가 포트레이트,
  드레스 개별 컷)은 빈칸이 아니라 미확정 토큰으로 렌더해야 한다.

### 5.3 사진 파이프라인

- **REQ-PH-001** 크론은 6시간 주기로 계정 게시물을 전량 조회하고, 신규만 최대 해상도로
  내려받아 자사 스토리지에 원본을 보관해야 한다.
- **REQ-PH-002** 수집된 사진은 `UNSORTED` 상태로 저장되며, 관리자가 선택한 것만 `PUBLISHED`가 된다.
- **REQ-PH-003** `PUBLISHED`가 아닌 사진은 프론트에 노출되지 않아야 한다.
- **REQ-PH-004** 사진은 3개 언어 alt를 모두 갖추기 전에는 게시할 수 없어야 한다.
  UI와 API 양쪽에서 막아야 한다.
- **REQ-PH-005** 장변이 임계값 미만인 저해상도 사진은 경고 배지를 달아 원본 교체를 유도해야 한다.
- **REQ-PH-006** 「최근 작품」은 `PUBLISHED` 중 `takenAt` 최신순으로 자동 구성되어야 한다.
- **REQ-PH-007** 자격 증명이 없을 때 크론은 명시적으로 실패(503)해야 하며,
  성공한 것처럼 보고해서는 안 된다.

### 5.4 문의

- **REQ-IN-001** 문의는 DB에 먼저 저장되고, 알림은 그 다음이어야 한다.
  알림 실패가 저장 실패로 이어져서는 안 된다.
- **REQ-IN-002** 문의 API는 모든 입력을 스키마로 검증하고 필드마다 길이 상한을 둬야 한다.
- **REQ-IN-003** 관리자는 문의 문장을 그대로 FAQ로 승격할 수 있어야 한다.
- **REQ-IN-004** 고객 이메일 주소는 캐시·색인될 수 있는 어떤 페이지에도 렌더되면 안 된다.

### 5.5 관리자

- **REQ-AD-001** `/admin` 전체와 `/api/admin` 전체는 인증 없이 접근할 수 없어야 한다.
- **REQ-AD-002** `/admin`과 `/api`는 `noindex`여야 한다.
- **REQ-AD-003** 관리자 UI는 한국어이고, 편집 대상 콘텐츠는 원 언어를 유지해야 한다.
- **REQ-AD-004** 쓰기 경로가 아직 연결되지 않은 화면은 성공한 것처럼 보이면 안 되고,
  연결되지 않았음을 화면에 드러내야 한다.
- **REQ-AD-005** 플랜을 수정하면 홈과 상세 페이지가 함께 갱신되어야 한다(ISR 재검증 지점 확보).
- **REQ-AD-006** 분류 축을 추가하면 갤러리 필터와 URL이 자동 생성되어야 한다.
  term slug 변경은 공개 URL을 깨뜨리므로 경고해야 한다.
